# Deep Read — 模式 C：问题—现象—机制交叉矩阵

## 0. 在五 skill 流水线中的位置

本 skill 是证据整合层，唯一支持 Mode C。它消费 `ANALYSIS_PACKAGE`、实验记录或深挖报告，把它们统一成 `MODE_C_PACKAGE`，交给 `discover-innovation`。实验回流时，它也消费 `SQUEEZE_REPORT` 的 Mode C 输入包，做增量合并。

```text
ANALYSIS_PACKAGE / SQUEEZE_REPORT
              ↓
      deep-read（Mode C）
              ↓ MODE_C_PACKAGE
      discover-innovation
```

它不直接设计方法，不把候选连接点写成 Idea 卡片。

## 1. 唯一支持模式与适用范围

本 skill **仅支持模式 C**：把多个研究来源和/或已有实验材料整理成可核验的“问题 P × 现象 F × 机制 M”交叉矩阵，并输出供 `discover-innovation` 使用的结构化素材包。

适用于自然科学、医学、工程、计算机、社会科学、心理学、商科、教育、艺术研究等领域，也适用于计算实验、实验室实验、临床研究、田野研究、调查、模拟、工程测试和混合方法研究。

不预设模型、数据集、指标、样本类型、代码或某一学科术语。没有代码或结构化数据时，使用理论、观察、实验记录、协议、统计结果、质性编码、图表和补充材料作为证据。

### 不在本 skill 范围内

- 独立回答一篇论文的事实问题或写完整论文摘要
- 只做 Related Work/引用段落润色
- 直接设计新方法、模块、干预或完整实验方案
- 代替系统综述、联网检索、统计复现或正式同行评审

这些内容可以作为模式 C 的输入，但最终交付必须仍然是 P/F/M/E 结构化矩阵；需要方法设计时交给 `discover-innovation`。

## 2. 输入配置与证据边界

执行前先声明：

```text
模式：C（问题—现象—机制交叉矩阵）
研究领域/子领域：{领域}
研究主题或触发问题：{要寻找的瓶颈/空白/矛盾}
来源范围：{论文、报告、实验记录、代码、数据、协议等路径}
纳入规则：{时间、对象、任务、证据类型或用户指定范围}
现有矩阵/笔记：{路径或“无”}
上游交接包：{ANALYSIS_PACKAGE / SQUEEZE_REPORT / 其他来源；无则写无}
下游用途：{交给 discover-innovation / 研究规划 / 仅本次分析}
```

优先读取项目说明、研究计划、文献索引、论文笔记、实验记录和用户指定材料。路径不存在时记录为缺失，不用当前项目的固定文件名替代，也不假造未读取的结果。

每个结论必须标记证据层级：

| 标记 | 含义 |
|:--|:--|
| **SC** | source claim：作者/报告/实验记录明确声称的内容 |
| **DE** | direct evidence：可从结果、数据、代码、协议或图表直接核验的内容 |
| **AI** | analyst inference：基于来源的分析推断，必须写出推理链 |
| **UN** | unknown：当前材料不足以判断 |

不要把 SC 自动升级为 DE，也不要把 AI 写成来源结论。

## 3. 模式 C+ 工作流

```text
C0  定义主题、边界和纳入来源
 ↓
C1  建立来源—证据地图
 ↓
C2  提取问题 P 与现象 F
 ↓
C3  追踪机制 M、条件和反例
 ↓
C4  做跨设置复验与证据强度审计
 ↓
C5  构建 P × F 交叉矩阵
 ↓
C6  筛选非平凡、可检验的连接点
 ↓
C7  输出 Mode C handoff package
```

### C0：定义主题与边界

将用户问题改写成最多 1–3 个矩阵目标，例如：

- 哪些已观察现象可能解释某个重复出现的问题？
- 哪些论文共享一个尚未检验的假设？
- 哪些矛盾结果来自不同的对象、测量、任务或实验条件？

明确时间、对象、研究类型和证据纳入规则。若用户只给了“找创新”，不要直接发明方案，先把它转换成一个可构建的矩阵目标。

### C1：建立来源—证据地图

优先选择与主题最相关且证据互补的来源，通常 3–8 个；来源过多时分批处理。建立：

| 来源 ID | 来源与版本 | 类型 | 对象/样本/材料 | 直接可用证据 | 需核验部分 |
|:--|:--|:--|:--|:--|:--|
| S01 | {标题/实验名/版本} | {论文/数据/代码/协议/日志} | | | |

记录稳定定位：章节、页码、表图、补充材料、代码文件/函数、数据字段、日志行、样本编号或协议步骤。没有稳定定位时标记“定位不足”。

### C2：提取问题 P 与现象 F

只保留具体、可追溯、可区分的条目。一个条目只表达一个核心命题。

**问题 P** 包括：

- 可重复的误差、瓶颈、失败案例或未满足需求
- 已知方法的边界、矛盾结果或未解决限制
- 一个明确、可检验但尚未回答的问题

**现象 F** 包括：

- 数据、实验、观察、代码或多篇来源支持的规律
- 反常结果、异质性、非线性、阈值、漂移、相变或异常样本
- 与方法设计无关但可作为研究素材的性质

为每一项填写：

| ID | 类型 | 一句话描述 | 对象与条件 | 证据标记 | 证据强度 | 定位 |
|:--|:--|:--|:--|:--:|:--:|:--|
| P01/F01 | P/F | {具体命题} | {何时、对谁、在什么设置} | SC/DE/AI | 高/中/低/未知 | {位置} |

不要把“整体性能不高”“方法很复杂”“存在研究空白”直接作为 P；先拆成可观测、可比较的具体问题。

### C3：追踪机制 M、条件和反例

对每个 P/F 强制建立最短可解释链：

```text
观察到什么 → 哪个操作/测量/假设/过程可能产生它 → 通过什么中间证据连接到结果
```

机制条目必须写明：

| M ID | 关联 P/F | 机制或解释 | 支持证据 | 依赖条件 | 反例/替代解释 | 当前状态 |
|:--|:--|:--|:--|:--|:--|:--|
| M01 | F01 | {为什么发生} | {E IDs} | {条件} | {替代解释} | 已支持/部分支持/待检验 |

至少检查以下边界：对象/样本、任务、时间尺度、剂量或强度、设备/实现、测量方式、数据分布、统计功效、操作者和资源预算。若不知道机制为什么成立，保留为“现象—问题连接候选”，不得写成机制已确定。

### C4：跨设置复验与证据审计

对每个候选 F×P 连接，完成四项审计：

1. **来源内复核**：现象是否由原始数据/图表/代码/协议支持，而不只是摘要声称？
2. **跨设置复验**：换一个样本、任务、测量、设备、时间或分析规格后，信号是否仍可能存在？
3. **证据路径**：F → M → P 的每个箭头是否有证据，哪里只是推断？
4. **独立性**：连接是否只是同一来源重复描述，还是跨来源提供了互补信息？

用以下状态代替过度确定的二元判断：

| 状态 | 含义 |
|:--|:--|
| ✅ supported | 至少有直接证据且机制路径基本完整 |
| ◐ plausible | 有合理证据，但跨设置或机制仍需检查 |
| △ diagnostic-needed | 值得做低成本诊断，但现有材料不足 |
| — unsupported | 当前材料没有形成可靠连接；记录理由，不扩张结论 |

“unsupported”只描述当前证据，不等于研究问题不存在或方向没有价值。

### C5：构建 P × F 交叉矩阵

矩阵单元必须同时包含状态、理由和证据 ID：

| | P01 {问题} | P02 {问题} | P03 {问题} |
|:--:|:--:|:--:|:--:|
| F01 {现象} | ✅ F01×P01：{机制/证据} | ◐：{缺什么} | —：{不兼容原因} |
| F02 {现象} | △：{建议诊断问题} | ✅：{机制/证据} | ◐：{边界条件} |

矩阵不是“论文 A × 论文 B”的简单拼接。每个单元需要指出：

- 是否在同一对象、尺度或数学/因果框架上
- F 是否可能缓解、解释、暴露或重新定义 P
- 连接是否依赖某个分类器、操作者、数据切分、设备或其他隐藏条件
- 连接后是否出现新的冲突、反馈、优化、识别或伦理问题

### C6：非平凡性与可检验性筛选

只输出值得移交的连接点，不设计最终方法。对每个 ✅/◐/△ 连接评分：

| 维度 | 0 分 | 1 分 | 2 分 |
|:--|:--|:--|:--|
| 机制完整度 | 不知道为何连接 | 有部分链条 | 机制和条件清楚 |
| 证据质量 | 仅作者声称 | 有间接/单一证据 | 有直接且可定位证据 |
| 跨设置潜力 | 明显只适用于原设置 | 需要适配验证 | 有合理迁移依据 |
| 非平凡性 | 直接照搬/拼装 | 有接口适配 | 产生新问题或新理论约束 |
| 新颖性状态 | 已有同类明确处理 | 相近工作需比较 | 尚未发现同类但需检索 |
| 可验证性 | 成本或伦理不可接受 | 需要 pilot | 有清晰低成本起点 |

总分只用于排序，不替代判断。任何“新颖性”结论都要注明检索范围和未知部分；Mode C 不把连接点改写成 Idea 卡片。

## 5. 上游输入与下游接口约定

### 5.1 可消费的上游包

`deep-read` 可以消费以下两类标准包：

| 上游包 | 必须读取 | 转换方式 |
|:--|:--|:--|
| `ANALYSIS_PACKAGE` | 来源版本、研究问题、设计、结果不确定性、候选 P/F、证据索引、限制 | 将候选 P/F 重新核验并补 M/E/边界 |
| `SQUEEZE_REPORT` | 实验记录 ID、新 P/F/M、稳健性、替代解释、证据索引、`mode_C_input_bundle` | 将新现象放回文献/来源矩阵，标出增量与冲突 |

也可直接读取论文、报告、实验记录、代码、数据和协议，但必须先建立来源—证据地图，不能把未定位的摘要或口述当成 DE。

### 5.2 交给 discover-innovation 的标准包

`discover-innovation` 只应消费 `MODE_C_PACKAGE` 中的 `P/F/M/E/C` 字段以及边界、证据状态和第一项低成本核验，不应把普通问答、跨论文表格或写作段落当作模式 C 结果。

下游读取顺序：

```text
1. 读取元数据与来源地图
2. 验证 P/F/M/E IDs 和证据定位
3. 选择一个 C ID，不同时改动多个连接点
4. 将 C ID 映射到一个创新模式
5. 再设计假设、对照、指标和最小验证
```

如果输入是旧格式矩阵，先补齐 ID、证据标记、机制条件、替代解释和状态；补不齐时标记 `UN`，不得静默当作高置信素材。

### 5.3 回流规则

`SQUEEZE_REPORT` 不能直接作为新的 `IDEA_PACKAGE`。先读取其 `mode_C_input_bundle`，将新发现编号为 P/F/M/E 并与旧矩阵合并；只有形成新的 `MODE_C_PACKAGE` 后，才进入下一轮 `discover-innovation`。

## 6. 渐进式披露与上下文控制

- C0–C1 只读取索引、摘要、目录和实验元数据。
- C2 读取与 P/F 直接相关的章节、图表、日志或结果。
- C3–C4 只有在连接点需要时才读取方法、附录、代码、协议或原始数据。
- C5–C6 只围绕入选 P/F 组合做综合，不重新加载无关来源。
- 上下文接近容量上限时，先保存当前来源地图和 P/F/M/E 表，再继续；不牺牲证据定位换取条目数量。

## 7. 持久化规则

只有用户要求或项目工作流要求时才写文件。推荐文件名：

```text
{日期}-mode-c-cross-matrix-{主题}.md
```

写入前先读取已有矩阵，采用新版本/追加章节，保留旧结论、来源、时间和状态。新现象、新问题和机制修正必须注明来源和证据位置；不得直接覆盖历史矩阵。

## 8. 禁止行为

- 不输出模式 A/B/D，也不把本 skill 当作普通论文问答或写作 skill。
- 不从摘要、作者意图或单次实验直接推出普遍机制。
- 不把“相关”写成因果，不把 AI 推断伪装成 SC/DE 证据。
- 不因一次复验不足就把问题或现象写成不存在；只描述当前证据状态。
- 不把简单的 A+B 拼装标为非平凡创新；先检查是否产生新约束或新问题。
- 不越过 handoff 边界直接设计最终方法；方案设计由 `discover-innovation` 接手。
