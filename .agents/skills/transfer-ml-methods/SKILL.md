# 跨领域机器学习方法迁移

围绕“如何让源方法的作用机制在目标系统中成立”设计迁移。最终给出有证据起点、明确生效条件、可被实验否证的方案；证据不足时给出诊断计划，不承诺一定能找到有效 idea。

## 范围与起点

- **A**：用户的 AI／机器学习目标任务和现有 Baseline。
- **B**：其他领域中解决相同或相似底层困难的源方法；来源可以是机器学习，也可以是相关学科。
- **C**：把 B 用到其他任务中的已有迁移案例，可没有，可有多个。
- **A′**：为满足 B 的生效条件而适配后的 A；**A′+B**：适配后应用 B 的系统。

先读取用户指定的论文、代码、配置、实验记录和已有分析。只确认影响判断的缺口：目标任务与 Baseline、失败现象及发生条件、已有证据、候选 B（如已指定）、评价标准与资源约束。信息可从材料得出时直接使用，不要求用户重填表格。

用户未说明目标问题时，先澄清问题；只有方法名称时，先核实具体论文或版本。缺少日志或实验不妨碍提出假设，但结论必须保持条件性。资料无法访问时说明缺口，不能声称读过原文。

按用户当前阶段进入流程：已定位的问题不用重新穷尽诊断；指定了 B 就重点核验 B；只问可迁移性就交付条件判断。仅当已有结论缺少关键证据时回补。默认停在方案和验证设计，用户后续明确要求实现或运行实验时再进入相应工作。

## 证据约定

区分 **原文主张、直接证据、分析推断、未知**。论文作者的机制解释不自动等于因果证明；代码能证明某运算存在，也不单独证明它造成性能变化。对影响迁移决策的结论附来源定位：论文章节／公式／图表，或代码路径与行号、实验配置与记录。

执行检索时优先核验论文原文、补充材料和官方代码。摘要或二手介绍只能支持初筛。无检索能力时可分析用户材料并给出检索式，不能把拟检索内容写成找到的论文。

## 工作流

### 1. 将 A 的失败现象落到可检验机制

使用 **1a–1b–2a–2b** 循环：

1. **1a 观察**：记录失败现象、发生条件和对照，定位具体样本、训练阶段、模块或运算。
2. **1b 归类**：按可共同解释的现象分组，保留组间差异和反例。
3. **2a 追问**：提出候选原因、竞争解释，以及能够区分它们的观察或干预。
4. **2b 串联**：写出因果链，每条关键连接标明证据或待验证状态。

一轮后说明新增发现与尚未解释的问题。有新证据或有区分力的检验时继续深入；达到可检验的机制层级，或后续只能重复推测时停止。模块、运算、算子是可能的定位层级，不是每个问题必须钻到的终点。

将结果压缩成机制问题，例如“在条件 X 下，运算 Y 引起现象 Z，候选原因是 M”。不要在机制未确认时把候选原因称为根因。证据不足时，可以依据多个竞争假设条件性地搜索 B。

### 2. 按底层问题寻找 B

以机制问题、同义表述、关键数学性质和生效条件构建检索式，逐步扩展到其他领域；任务名作为辅助约束。用户指定数据库、年代或来源时遵守其范围。

初筛后读原文确认：问题发生在哪个环节、方法实际改变了什么、结果在什么条件下成立。名称相同、表面结构相似或摘要出现相同术语，都不足以判定机制可迁移。

保留有实质机制联系的候选，说明纳入／排除理由；不设凑数目标。只有来源线索的候选标为未核验，不能据此确认可迁移性。选定或推荐深入对象前，比较机制匹配、生效条件缺口、适配代价和可验证性。

### 3. 分析 B 为什么有效、何时有效

对深入对象回答：

- **原始问题**：B 针对的具体缺陷，而非只列最终指标。
- **作用机制**：从输入到核心运算、输出、训练信号的作用链；用公式、伪代码或结构说明真正产生作用的部分。
- **生效条件**：表示形式、数据分布、采样方式、结构连接、可用监督、优化目标及计算要求中，哪些关系到作用机制成立。

把条件区分为“已检验的必要条件”“证据支持的生效条件”“分析推断”“未知”；原论文使用了某设置，不等于证明该设置不可缺少。记录失效边界、负结果和替代解释；没有相关实验时明确证据缺失。

### 4. 用 C 研究迁移中的改造

检索 B 的引用、扩展及跨任务应用，核实 C 是否使用了 B 的核心机制。对比 B 与 C 的输入输出、连接方式、训练目标、数据假设和实现变化。

逐项区分任务接口适配、可能维持机制的条件、工程选择及额外贡献。C 成功的最终指标不能单独证明某项改造必要，也不能证明全部收益来自 B。

没找到 C 时记录已查范围和缺少的证据，仍可形成待验证方案；不得把“未找到”写成“没有人做过”。C 的失败或适用范围收缩同样可以约束迁移方案。

### 5. 设计让 B 的条件在 A 中成立的适配

逐项检查 B 的条件在 A 中是 **已满足、可通过适配建立、不满足、未知**。对可建立的条件，说明 A 的哪一环节要改变、如何产生所需表示或信号、以及怎样测量条件确实成立。

优先检查通过改造 A 的 Baseline 建立条件的可能性。保留 B 的核心作用机制，但不把“必须改 A”当作普遍结论；改 B 更合理时解释机制如何保留以及权衡。条件无法建立、改造损害任务或成本超出约束时，给出放弃／暂缓理由。

形成可检验假设：**若 A′ 建立条件 S，B 将通过机制 M 改善目标现象 Z；可观察预测为 P，若出现结果 F 则该假设不获支持。** 区分已知关系与预计关系，不把设计写成已实现或已获收益。

### 6. 拆分适配收益与方法收益

验证设计至少覆盖概念上的三组；当前只输出设计，无需实际运行：

| 组别 | 内容 | 回答的问题 |
| --- | --- | --- |
| A | 原始 Baseline | 当前起点是什么 |
| A′ | 仅进行条件适配 | 适配本身是否带来收益 |
| A′+B | 适配后加入源方法 | 在适配系统中，B 是否有增量作用 |

尽量保持数据划分、预处理、训练／调参预算和评价协议可比；记录参数量与计算成本等额外变化。不能控制的重要差异需写成归因限制，不能把组间差异直接归因于 B。

同时测量 **条件是否建立、目标失败现象是否改善、机制预测是否出现、整体指标与稳定性**。按效应大小和资源约束选择重复次数与不确定性报告方式，不固定种子数量。

需要区分条件依赖或核心运算贡献时，再加入可行的 A+B、破坏条件、移除核心运算、匹配额外容量／计算预算等对照。若实现不成立，解释原因；不为凑齐实验矩阵设计无意义组别。为各关键假设写出支持和否证判据，区分“方案尚待实验”和“已验证有效”。

## 交付

先给判断及其依据：值得最小验证、需先补证据、或当前不适合迁移。按用户所问阶段调整篇幅，完整方案应让读者能追踪 **A 的证据 → B 的机制与条件 → C 的适配经验 → A′ 的改造 → 验证与否证**。

整理完整迁移方案或多候选比较时，读取 [references/transfer-design.md](references/transfer-design.md) 中的条件表与验证模板；短问答不必加载模板。结束时列出最有区分力的下一步和关键未知项，不强行生成新方法或声称创新性已证明。
