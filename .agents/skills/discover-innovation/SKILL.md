# Discover Innovation — 通用研究创新发现

## 0. 在五 skill 流水线中的位置

本 skill 是方案生成层，消费 `deep-read` Mode C 的 `MODE_C_PACKAGE`，从一个已定位的 `C` 连接点生成可执行、可归因的 `IDEA_PACKAGE`，交给 `record-experiment`。它不把一次实验结果直接当作创新结论。

```text
MODE_C_PACKAGE → discover-innovation → IDEA_PACKAGE
                                      ↓
                              实际执行研究
```

## 适用范围

本 skill 适用于自然科学、医学、工程、计算机、社会科学、心理学、商科、教育、艺术研究等领域，兼容计算实验、实验室实验、临床研究、田野研究、调查、模拟、设计研究和混合方法。

“创新”不等于增加模块或追求单一指标上升。这里的目标是找到一个有证据起点、能解释其价值、可以被反驳或修正、并且适合当前资源与伦理边界的研究问题或方法。

## 前置读取与研究配置

执行前优先读取：

- 已有文献综述、阅读笔记、数据分析和实验记录
- 研究计划、预注册、项目日志或已有假设
- 已尝试的方法、结果、限制和未回答问题
- 用户指定的领域规范、评价指标、数据字典、实验协议或伦理要求

路径不存在时跳过并说明，不要把当前项目的专用文件名当作通用前提。先声明：

```text
领域/子领域：{领域}
研究对象与任务：{研究什么}
当前证据：{已有数据/文献/观察/方法}
资源边界：{时间、样本、设备、算力、预算}
主要评价标准：{指标/效应/可用性/理论解释力}
伦理与合规边界：{隐私、安全、受试者、材料、环境等}
```

若用户尚未给出领域，不必强行猜测；用“跨领域通用描述”提出候选，并列出需要确认的术语和约束。

## deep-read Mode C 输入契约

当输入来自 `deep-read` 时，只接受 **Mode C handoff package**。它至少应包含：

| 字段 | 内容 | 用途 |
|:--|:--|:--|
| `P` | 具体问题及对象/条件 | 定义要解决的缺口 |
| `F` | 有证据支持的现象及边界 | 提供可利用或可解释的观察 |
| `M` | 机制链、依赖条件和替代解释 | 防止把相关性当成机制 |
| `E` | 证据类型、来源定位和可信度 | 检查可追溯性 |
| `C` | P×F 连接、状态、评分和未知项 | 选择一个创新入口 |

先验证 ID、证据定位和状态，再选择一个 `C` 连接点。旧版只有“论文 A × 论文 B”或只有 ✅/❌ 的矩阵，需要先补齐 `M/E/边界/状态`；无法补齐的字段标为 `UN`，不得默认为已验证。

Mode C 只提供问题、现象、机制和候选连接，不提供最终方法。`discover-innovation` 从 `C` 连接点开始设计假设、对照和最小验证，不重复替 deep-read 做文献摘录。

## 工作原则

1. 先找真实问题，再设计新颖形式。
2. 每个想法都要有证据来源、机制解释、可检验预测和失败判据。
3. 区分“把已有方法换到新场景”与“解决了迁移后产生的新问题”。前者可能有应用价值，但不能自动称为方法学创新。
4. 新颖性必须通过文献和已有项目检查；不能凭记忆断言“没人做过”。
5. 一次只深入一个主切入点，同时保留未选候选及未决假设。
6. 对一个结果不足以支持的强结论，使用“在当前设置下未观察到”“证据支持到这里”为准。
7. 设计优先考虑低成本诊断、清晰对照和可复现性，而不是盲目扩大实验规模。

## 工作流

```text
Step 0  配置研究边界与成功定义
   ↓
Step 1  选择一个创新切入点
   ↓
Step 2  追问机制、边界条件与现有证据
   ↓
Step 3  生成可检验的最小方案
   ↓
Step 4  三层质量检查：新颖性、研究价值、可归因性
   ↓
Step 5  输出 Idea 卡片与验证计划
```

## Step 1：选择切入点

优先从 `deep-read` 的 **Mode C P×F 交叉矩阵**中选择一个带有证据、机制和边界条件的 `C` 连接点；其次使用已有实验的异常结果或用户明确提出的痛点。没有 Mode C 矩阵时，可直接使用后两类材料，但必须先补齐问题、现象、机制、证据和可检验边界，再进入创新设计。

| 模式 | 从哪里开始 | 适合回答 |
|:--|:--|:--|
| 1. 问题驱动 | 可重复的误差、瓶颈、失败案例或未满足需求 | 为什么在某类条件下失效，如何针对性修正？ |
| 2. 现象驱动 | 反常、异质性、非线性、相变或意外相关 | 这个规律为何出现，能否成为新的解释或测量？ |
| 3. 假设挑战 | 领域中默认但少被检验的前提 | 去掉、反转或改变该前提后会发生什么？ |
| 4. 跨领域启发 | 另一个领域解决相似结构问题的方法 | 哪些机制可迁移，迁移后新增什么挑战？ |
| 5. 系统/架构审查 | 现有流程中的未验证组件、接口或耦合 | 哪个设计选择缺少证据，如何做最小替代对照？ |
| 6. 任务/设置扩展 | 现实需求与现有基准的落差 | 新场景、约束、群体、时间尺度或评价目标如何改变问题？ |

只选一个主模式深入。若用户已有明确现象，默认优先 Pattern 2；若用户已有明确瓶颈，优先 Pattern 1。

## Step 2：六种模式的标准操作

### Pattern 1：问题驱动

```text
1. 收集可重复的错误、失败案例、低效环节或用户痛点。
2. 按机制而不是表面现象归类，保持问题定义互斥且可量化。
3. 追溯到操作、测量、模型、流程、资源或假设层面的根因。
4. 为每个根因提出一个最小修正，并写出可能的替代解释。
```

### Pattern 2：现象驱动

```text
1. 记录现象的对象、条件、时间尺度和可重复性。
2. 用合适的统计、可视化或定性编码量化现象与不确定性。
3. 比较机制解释、混杂因素、测量伪影和选择偏差。
4. 设计能利用或解释该现象的方案，并预先写出反例。
```

### Pattern 3：假设挑战

```text
1. 把隐含前提写成具体命题：“在条件 C 下，改变 X 不会影响 Y”。
2. 明确什么结果会支持、削弱或修正该命题，不只设置“成功/失败”二元结论。
3. 设计最小对照：保留其他条件，改变一个关键前提。
4. 若证据削弱原前提，提出更精确的适用范围或替代机制。
```

### Pattern 4：跨领域启发

```text
1. 先说明源领域技术解决的结构性问题，而不是只搬运名称。
2. 映射两边的对象、关系、约束、反馈和评价目标。
3. 列出不可直接迁移之处：数据生成、测量尺度、因果结构、资源或伦理。
4. 把“迁移适配”转化为可检验的新问题，再设计最小验证。
```

### Pattern 5：系统/架构审查

```text
1. 画出从输入/材料到输出/决策的流程图。
2. 为每个步骤记录理论依据、默认参数、接口假设和已做消融。
3. 找出信息损失、反馈耦合、不可观测变量、单点故障和未验证依赖。
4. 每次只替换一个关键选择，设置公平的基线和资源预算。
```

### Pattern 6：任务/设置扩展

```text
1. 识别现有研究与现实使用之间的具体落差。
2. 将落差写成新的任务定义、约束或估计目标。
3. 说明数据、标注、样本、评价和伦理要求如何变化。
4. 先构建透明 baseline，再验证新设定是否产生有价值的差异。
```

## Step 3：把想法变成最小可检验方案

每个候选想法必须回答：

| 要素 | 必须写清楚 |
|:--|:--|
| 研究问题 | 一句话、对象明确、可在本项目资源内回答 |
| 核心假设 | 机制和适用条件，不写成口号 |
| 可检验预测 | 如果假设成立，哪个观测量会如何变化？ |
| 最小改动/干预 | 只改变关键因素，避免同时引入多个新组件 |
| 对照 | 基线、消融、替代解释和必要的阴性对照 |
| 主要结果 | 预先指定主要指标、效应大小和不确定性表达 |
| 解释结果 | 支持、部分支持、未观察到、与预期相反及其含义 |
| 资源与风险 | 样本、重复、设备、算力、时间、失败成本、伦理风险 |
| 后续分支 | 各种结果分别触发什么下一步，而不是只写“涨了就继续” |

对于高成本实验，先设计一个低成本诊断或小规模 pilot。每个诊断脚本、图表或分析尽量只回答一个明确问题；共享的数据提取可以复用，但分析问题要分开记录。

## Step 4：三层质量检查

### 1. 新颖性检查

- 检索同一问题、同一机制、同一数据/人群/任务和近似方法。
- 区分完全相同、同一机制的不同实现、相近但有关键差异、仅有应用迁移。
- 指出检索范围、时间、数据库和仍可能遗漏的部分。

### 2. 研究价值检查

- 若结果支持假设，能增加什么：新机制、边界条件、测量、方法、数据、理论或应用能力？
- 若结果不支持假设，是否仍能缩小不确定性或发现重要限制？
- 结论是否超过了数据、样本、设计或测量能够支持的范围？

### 3. 可归因性检查

- 结果能否归因于核心改动，而不是数据泄漏、调参、预算、样本差异、实现细节或偶然性？
- 是否有独立重复、不同随机种子、批次、操作者、数据切分或外部样本的计划？
- 是否有伦理、隐私、安全、受试者负担、环境影响或知识产权风险？

三层检查不是为了把想法简单判为“行/不行”，而是给出：当前证据、未决风险、需要补做的最小检查和建议投入等级。

## 5. 标准交接产出：IDEA_PACKAGE

在交给 `record-experiment` 前，必须将 Idea 卡片整理为以下字段。卡片中没有的字段不能由下游猜测：

```text
package_type: IDEA_PACKAGE
package_version: research-pipeline-contract v1.0
idea_id: {唯一 ID}
source_matrix_id: {MODE_C_PACKAGE 的 matrix_id}
selected_C_id: {单个 C ID}
source_P_ids / source_F_ids / source_M_ids / source_E_ids: {来源 IDs}
research_question: {问题}
hypothesis_and_mechanism: {假设与机制链}
testable_predictions: {可检验预测}
design_and_controls: {设计、基线、阴性/阳性/替代对照}
sample_materials_or_experimental_units: {样本、材料或实验单位}
primary_outcome_and_estimand: {主要结果与估计目标}
secondary_outcomes: {次要结果}
analysis_plan_and_uncertainty: {分析、重复、误差/区间、异质性处理}
resources_time_cost_and_risk: {资源、时间、成本和风险}
ethics_safety_privacy_or_compliance: {合规要求}
stopping_and_interpretation_rules: {停止规则和 A/B/C 解释规则}
status: exploration / diagnostic / pilot / formal-validation / deferred
next_skill: record-experiment
```

`record-experiment` 需要保留此包的原始版本，并用 `plan_version` 对照实际执行；因此“最小验证”必须足够具体，至少能回答改变了什么、与谁比较、测量什么、结果如何解释。

## 与其他 skill 的衔接

```text
deep-read Mode C
   └─→ P/F/M/E + P×F 矩阵 + C 连接点
           ↓
discover-innovation
   └─→ IDEA_PACKAGE（Idea 卡片 + 最小验证计划）
           ↓
实际执行研究 → record-experiment
                    ↓ EXPERIMENT_RECORD
              squeeze-experiment
                    ↓ SQUEEZE_REPORT
              deep-read Mode C（增量合并）
```

如果项目中有 `evaluate-idea` 或实验过滤器 skill，可将 Idea 卡片交给它们做独立复核；没有这些 skill 时，使用本文件的三层检查，不要假设它们一定存在。

## 禁止行为

- 不把简单复现、组件拼装或换数据集自动包装成方法学创新。
- 不用一次实验、单一指标或单一数据切分推出普遍结论。
- 不隐去不支持假设的结果、替代解释、统计不确定性和边界条件。
- 不同时改变多个关键因素后声称已经定位了机制。
- 不跳过伦理、隐私、安全、受试者权益、环境和知识产权约束。
- 不因一个结果不符合预期就直接放弃问题；先记录学到的限制并列出可区分的后续测试。
