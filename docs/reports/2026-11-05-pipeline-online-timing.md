# 从传感器量测到输出：完整链路与1Hz在线回放

2026-11-05，针对用户明确的“完整端到端、每秒更新一次”要求完成工程计时。[原规格](../../HandOver/L2S-20261105-pipeline-timing.md)、[接口失败保全及剩余项目修正](../../HandOver/L2S-20261105-pipeline-timing-repair.md)、[全部原件](/Users/a1/Projects/biye-ronghe/docs/evidence/20261105_pipeline_timing/)。不读真实身份标签/reference/test，不训练或拟合normalizer，没有产生新的精度/同行排名结论。

**2秒可以在线。** 在线的输入因果性、单次结果延迟、持续输出吞吐和数据新鲜度分别判断。1Hz是每秒一轮输出；若单个串行工作单元每轮耗时2秒、每秒来一轮，就会排队积压。两个具有足够独立算力的工作单元或流水处理，在任务依赖允许时可以保持每秒出一轮，但单轮仍约2秒延迟；若还要求小于1秒硬截止，则该2秒实现不满足。不能把“耗时2秒”直接称为不能在线，也不能用一组64query总耗时除64冒充实际增量步耗时。

## 完整应用计时边界

开始：应用收到一份原始传感器量测CSV字节缓冲。结束：全部输出组的成员、经纬度/速度/航向、query时间与单位已序列化为可发送的JSON bytes。包含：解码、合法性检查、排序/去重、匿名source/batch片段组装、Q64网格、原生OLS与支持证据、全部候选对特征/056网络、必要CTX及HARD/STRUCT网络、WS构组、全部融合/恢复、输出序列化。每方法独立重做这些步骤，没有把缓存motion/分数/分组当预测输入，也没有在方法间摊薄共同前端成本。

PTFM和DeepAF在本项目中是融合器，完整组合使用其实际共同056＋WS关联前端。我们的两条路线分别使用HARD175或STRUCT173＋完整159恢复＋178/O；159是178保持多支持输出的必要步骤，本次已计入。模型常驻，权重与训练normalizer冻结，原生OLS每次重新计算。硬件为共享Xeon E5-2620 v4、CPU16–19四线程，无GPU。未优化为增量或批量服务。

这里的“传感器量测”是项目已有的source、片段batch、时间、经纬度、速度、航向，不含雷达回波检测到航迹形成，因为项目没有该模块。无真实socket/传感器物理传输、消息排队/乱序/丢包/时钟偏差模拟，也没有输出网络发送/显示计时。统计的是应用收到数据到结果可发送的完整计算延迟，不虚报传感器物理采集到屏幕的所有延迟。

这表没有证明各架构在线不可行。实际增量部署应维护过去观测与状态，按新时刻更新；DeepAF当前评估入口逐组调用，已有forward_batch接口但这里没有改成批量/维护跨调用history；我们的物理特征、节点/组评分与恢复也逐窗口重算。缓存、分批/向量化与跨目标批处理有待实现和实测，不预先许诺优化后<1秒。原始全窗口数据允许查询之后的信息，是原离线评价的权限；本次prefix展示可只依当前已到数据计算，但输入范围/初始化/输出网格变化后精度尚未验证。

## 数据新鲜度与窗口等待

频率不等于新鲜度：到数截止减最新query的逻辑时间差，三场两次分别为.014/.972秒、.247/.134秒、0/.021秒；结果可发送时还需加上本次计算耗时。当前输出网格结束于最新有效观测时刻，没有强制外推到壁钟截止，因此不能用1Hz发布频率保证“状态只滞后≤1秒”。真实传输与乱序延迟未计。

本次回放用measurement timestamp模拟理想到达，不是实际设备arrival timestamp。过去历史缓冲在稳态可以保留，不必每秒重新等待整段历史；首次启动仍需最低观测量。若使用未来观测平滑或等待完整窗口，那部分等待必须另加。输入因果、缓冲积累、应用计算、排队/传输分别记录，不能用只前向2秒替整条在线响应。
